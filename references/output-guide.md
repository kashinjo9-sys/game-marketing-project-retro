# 用途输出与里程碑复盘指南

## 输出前确认

无论过去是否生成过同类材料，都确认本次：

- 给谁看；
- 具体要达成什么；
- 时长、篇幅或页面限制；
- 对方的评价标准或关注点；
- 输出形式和语言风格；
- 必须突出、必须回避的内容；
- 项目名、同事、合作方、金额和数据能否披露。

读取既有复盘后，只追问本次用途缺少的信息。

## 真实性处理

把材料分成：

- 可直接使用的强证据；
- 可以使用但需限定表述的内容；
- 需要补查的证据；
- 不建议使用的归因或结论。

直接告诉用户判断。用户坚持某个方向时，在不制造虚假事实或因果的前提下，选择更准确的措辞、位置和权重。

## 常见用途的选择逻辑

### 阶段沟通与向上汇报

- 强调最近变化、遗留问题、当前卡点和希望获得的支持。
- 准备口头表达顺序，不必把项目复盘全文搬过去。
- 既汇报结果，也说明下一步行动和需要负责人决策的事项。

### 转正答辩

- 选择能证明角色变化、学习速度、可靠执行、独立判断和业务意识的案例。
- 明确团队策略与个人贡献边界。
- 项目结果用于说明背景和业务价值，个人行动必须有独立证据。
- 展示真实不足及可观察的下一阶段目标。

### 年度述职与晋升

- 比较多个项目的角色范围、复杂度、判断空间、业务影响和方法迁移。
- 强调持续性和复用性，而不是只选一次偶然成功。
- 检查同类错误是否重复；未解决的问题不能包装成能力成熟。
- 根据当次职级或评价要求重新组织，但不反向修改项目事实。

### 简历与面试STAR

- 只保留与目标岗位相关的项目和动作。
- 使用能公开且可核实的数据。
- STAR不得抹掉上级决策和团队协作。
- 面试版本同时准备追问：为什么、如何判断、失败过什么、如果重做。

### 项目交接与团队SOP

- 从个人经历中抽取可复用流程、判断边界、检查项和升级机制。
- 区分“本项目偶然情况”和“可泛化做法”。
- 不把对某个同事或合作方的评价写进SOP。

### 新用途

不要套用最相近的旧模板。先识别新用途的受众、决策需求和证据标准，再从母版选择信息；必要时提出新的缺口问题。

## 跨项目成长分析

先阅读用户指定项目，再寻找自然出现的变化：

- 承担范围和项目复杂度；
- 独立判断与决策边界；
- 对业务目标、用户和市场的理解；
- 风险前置和问题闭环；
- 跨部门或外部合作方推动；
- 数据使用和创意验证；
- 经验是否迁移为下一次动作；
- 他人信任、授权和反馈的变化；
- 重复错误与尚未解决的短板。

先从项目发现成长，再对应本次里程碑评价要求。不要提前把所有项目塞进固定能力矩阵。

## 交付结构

根据用途选择最轻的有效形式：口头提纲、问答准备、项目故事、证据清单、文档、PPT大纲、简历条目或SOP。不要因为信息多就默认生成长文档。
